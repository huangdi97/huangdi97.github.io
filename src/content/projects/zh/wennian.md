## 概览

知身·问年不是一次衰老检测。它是一个决策引擎：估算一个人在多个衰老轴上的位置，判断真正驱动该画像的是哪个轴，并推理应当先改变什么。

开源 MVP 覆盖三项能力：衰老全谱评估、结构化健康访谈、白标报告生成。评估之后的所有环节——驱动维度识别、干预优先级、报告内容——都来自同一条流水线，因此页面上的数字与它背后的推理不会各说各话。

## 问题

衰老评估产品通常朝两个方向失败。

第一种失败是算数。单一时钟吃下一份血检单，返回一个数字：「你的生物学年龄是 41.3 岁」。这个数字难以行动、难以解释，而且通常不带区间。两个输出相同的人，底层画像可能完全不同。

第二种失败是叙事。把一个聊天机器人摆在化验报告前面让它解读。解读读起来很流畅，但没有任何契约：没有结构、没有置信边界、没有记录说明哪个假设产出了哪个结论，也没有可靠机制阻止它滑向医疗建议。

两种失败同一个根因：难点不在模型，而在模型周围的契约——什么被测量、什么被推断、什么被假设、什么明确不在范围内。

## 为什么重要

干预决策本质上是排序决策。如果一个画像主要由血管衰老驱动、其次由代谢衰老驱动，那么排序比头部数字更重要——而单个标量无法表达这一点。

输入质量同样是个问题。人们带来的是感受，不是指标：「下午总是很累」「半年前睡眠开始崩了」。这些表述确实有信号，但必须先被翻译为评估维度。把这个翻译交给自由对话，下游评估就只能在「恰好被提到」的内容上工作。

## 产品 / 研究主张

三条主张塑造了整个系统。

1. **衰老是多维的，输出也必须是多维的。** 标量生物学年龄是汇报上的便利，不是状态描述。
2. **输入质量比模型质量更关键。** 在评估之前做结构化主动追问，比在更差的输入上换一个更好的时钟更有效。
3. **干预建议是一种主张，主张就需要稽核。** 任何可能被用户据此行动的输出，都必须通过红线扫描，并声明适用范围。

## 系统设计

流水线刻意保持线性，并且包含一个无法跳过的校验阶段：

```text
输入 → 校验 → 时钟 → 器官时钟 → 融合器
     → 驱动维度识别 → 干预推理 → 稽核 → 报告
```

访谈阶段运行在评估**之前**，并写入融合器所消费的同一套维度模型。因此访谈发现与 biomarker 发现是同一量纲上的东西，而不是两条平行叙事。

## 架构

按执行顺序分层：

- **Inputs** — 类型化数据模型与校验，覆盖时钟所需的九项常规血检指标（白蛋白、肌酐、血糖、CRP 等）。
- **Clocks** — PhenoAge、KDM、DNN、LifeClock 四个时钟实现。
- **Dimensions** — 器官级时钟，覆盖心、肝、肾、脑、肺、血管、免疫、骨骼肌，用于呈现器官间的衰老异步性。
- **Integrator** — 融合时钟输出，识别主驱动维度，推导干预优先级。
- **Agents** — Analyst、Auditor、HealthInterviewer 等角色，各自职责边界明确、输出可检查。
- **Knowledge** — 症状—衰老维度映射库，覆盖 100+ 常见主诉。
- **Validation** — 输入校验、红线扫描与数值守护。
- **Outputs** — 报告构建与 PDF 渲染，每页附带免责声明。
- **Commercial** — 白标品牌配置（Logo、名称、主题色），支持 CSV 批量生成并打包为 ZIP。
- **API / UI** — FastAPI 接口与本地使用的 Gradio 界面。

## 核心能力

**衰老全谱评估。** 九项常规血检指标驱动四个经典时钟，叠加器官时钟层。输出包括器官系统画像、异步性读数、主驱动维度与干预优先级清单。所有预测附带置信区间。

**结构化健康访谈。** 用户用自然语言描述身体感受，访谈智能体最多进行三轮追问，并依据症状—维度映射库锚定真实评估维度，而不是临场发挥。访谈结果直接进入评估环节。

**白标报告生成。** 体检中心与长寿诊所可自定义品牌。报告包含器官雷达图、生物学年龄总结、干预建议与逐页免责声明。批量模式支持上传 CSV 并打包下载。

## 技术决策

**四个时钟，而不是一个。** 单一时钟容易交付，但无法自证。同时运行 PhenoAge、KDM、DNN、LifeClock 会让分歧显形，而时钟之间的分歧本身就是信号。

**器官时钟作为独立一层。** 器官级衰老独立于全局时钟推导。全局生物学年龄与器官异步性回答的是不同问题，不应被压成一个数字。

**有界的访谈。** 最多三轮，且映射到固定主诉库。无界对话只会产生无界输入，而无界输入无法被校验。

**稽核不是可选项。** 所有输出都要经过红线扫描，拦截医疗建议与处方内容。这是在流水线里强制执行的，而不是在提示词里请求一句。

**默认本地。** 隐私模式下数据不离开用户设备。衰老画像属于一个人能产生的最敏感的数据之一，架构把它当作需求而不是开关。

## 工程实现

仓库按与流水线阶段对齐的模块边界组织：`core`、`clocks`、`dimensions`、`integrator`、`causality`、`agents`、`knowledge`、`inputs`、`outputs`、`validation`、`commercial`、`api`、`ui`。配置集中在 `config/` 下的 YAML，能改配置解决的行为就不改代码。

系统本地运行——`python src/ui/app.py` 在 `127.0.0.1` 提供服务——测试使用 `pytest` 运行。

公开代码仓库：`WenNian`。本页使用的产品品牌是「知身·问年」；代码仓库与本页 URL 保留原始 `wennian` slug，以免既有链接与已索引的 canonical 失效。

## 验证

校验环节属于正常路径，而不是独立的 QA 阶段：

- **输入校验与数值守护** 在任何时钟运行之前拦截越界指标。
- **置信区间** 附在预测上，点估计永远不会单独出现。
- **红线扫描** 拦截生成内容中的医疗建议、处方与诊断性表述。
- **自动化测试** 覆盖时钟实现、融合器行为与报告构建。
- **逐页免责声明** 在产物本身声明报告范围，让边界随文档一起走。

## 当前状态

开源版本是覆盖上述三项能力的 MVP，作为可自托管的本地应用分发。

关于许可证有一处尚未确定：README 声明 GPLv3，但 GitHub 未在该仓库检测到 LICENSE 文件。在这一点被澄清之前，许可证状态应视为“未确认”而非“已确定”。

明确不在范围内：它不是诊断设备，不提供医疗建议，不开具处方。报告中明确声明其内容仅描述健康趋势，不构成医疗诊断。

## 我学到了什么

访谈环节是杠杆最高、也最不显眼的组件。提升输入质量对评估的改善，超过调整聚合策略——在花时间提升模型复杂度之前，这是一个值得先知道的结论。

稽核环节也反过来改变了系统其余部分的写法。一旦输出必须通过红线扫描，下游组件就只能产出结构化主张而非散文，这个约束让它们变得更好。
