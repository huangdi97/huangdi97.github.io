## 概览

PDIG（Personal Digital Infrastructure Graph，个人数字基础设施图谱）是一份规范与设计，用于把一个人的数字基础设施建模为依赖图谱：服务、设备、账号、凭据、数据存储，以及它们之间的关系。

有两件事它不是。它不是联系人管理工具——节点是基础设施，不是人。它也与 Broad Institute 的 DepMap 项目无关；名称上的巧合不代表任何领域上的关联。

塑造一切的设计约束是：图谱留在用户自己的设备上。没有托管账号体系，没有必须可达的服务端，也不假设同步一定存在。

## 问题

个人数字基础设施已经复杂到无法凭记忆掌握，而目前没有工具处理它。

一个人现在运转着数十个服务、设备与账号，它们之间存在真实的依赖关系：这个域名通过那家服务商解析；这个备份依赖那个凭据；这台设备是那个账号唯一的恢复路径。这些依赖通常在故障发生时才被发现——而那是最糟糕的发现时机。

现有工具各自覆盖其中一片——密码管理器、资产清单应用、监控面板——但每个都用自己的 schema 建模自己的那一片，没有一个把依赖结构本身当作关注对象。

## 为什么重要

依赖图谱能回答清单类工具回答不了的问题。不是「我有哪些账号」，而是「如果这家服务商没了，什么会坏，按什么顺序坏」。这是一个图问题，而且只有在关系被作为一等数据建模时才可回答。

本地优先约束之所以重要，取决于这个产物本身是什么。一份完整的个人基础设施地图是高价值目标。托管服务要持有它，就必须被信任到大多数人不应愿意给予的程度；把它留在设备上，是移除这个信任需求，而不是管理它。

## 产品 / 研究主张

1. **一份 canonical 规范，多个原生实现。** 模型只规定一次；每个平台以原生方式实现，并用共享测试套件证明一致性。
2. **本地优先是正确性属性，不是功能。** 图谱必须在无网络、无服务端的情况下完全可用。
3. **用密码学替代账号体系。** 身份与完整性由用户持有的密钥提供，因此不存在「谁拥有什么」的中心化登记。
4. **在平台期待原生的地方使用原生 UI。** 各平台在存储、权限与后台执行上的约定差异足够大，一套共享 Web 壳会同时和三者为敌。

## 系统设计

```text
canonical 规范（schema + 语义 + 不变量）
        │
        ├── 一致性测试套件（共享）
        │
        ├── Android 实现 ──── 原生 UI
        ├── iOS 实现 ──────── 原生 UI
        └── HarmonyOS 实现 ── 原生 UI
                    │
              仓储层（本地持久化，同步可选）
                    │
              密码学层（身份、完整性）
```

规范是契约。一致性套件才是让「已在三个平台实现」成为一项可被检查、而非仅被声称的事情的机制。

## 架构

**Canonical 规范。** 节点与边的类型、不变量，以及每种关系的语义——包括一个节点依赖另一个节点意味着什么，以及传递性故障如何计算。

**一致性套件。** 与平台无关的测试套件，由每个实现运行。这是防止三份原生代码库漂移到变成三个不同产品的机制。

**仓储层。** 本地持久化，采用同步可选设计：在未配置同步时必须完全可用，并且把同步视为一项不能破坏本地状态的附加能力。

**密码学层。** 基于密钥的身份与完整性校验，替代托管账号体系。密钥归用户所有，不存在中心化登记。

**原生 UI。** Android、iOS、HarmonyOS 上的平台原生界面。存储、权限与后台执行模型差异显著，设计接受三套 UI，而不是一套处处妥协的 UI。

## 核心能力

**依赖建模。** 基础设施节点之间的类型化关系，并支持传递性故障传播。

**一致性测试。** 一套共享套件在每个平台运行，使跨平台声明可被验证。

**本地优先持久化。** 一切在离线状态可用；同步可选且不可破坏数据。

**密码学身份。** 在不依赖托管账号体系的前提下提供身份与完整性。

**影响分析。** 给定某个节点，计算什么依赖它、按什么顺序失效——这正是整张图存在的意义所在。

## 技术决策

**先规范，后实现。** 在任何平台代码之前写出 canonical 模型，才让一致性测试成为可能。

**用共享一致性套件防止漂移。** 三份原生实现一定会漂移，除非有东西强制它们不漂移。套件就是那个东西。

**不要托管账号体系。** 引入它会重新带回这个项目正是要规避的信任需求。

**每个平台一套原生 UI。** 跨平台 Web 壳意味着要与每个平台的存储和权限模型对抗。代价是三套 UI；收益是没有一套是坏的。

**同步可选，绝不必要。** 如果同步可能破坏本地状态，本地优先的保证就是空的。

## 工程实现

规范是首要产物：schema、不变量与语义，写得让实现可以被对照检查。实现应当可以独立替换，而不必改动规范。

仓储层被设计为可脱离 UI 单独测试；密码学层位于其下，因此完整性保证不依赖存储引擎。

## 验证

不汇报任何结果；这是规范与设计。计划中的验证方式：

- **一致性对等** — 所有实现通过共享套件；出现偏差属于构建失败，而不是已知问题。
- **离线完备性** — 在禁用网络且未配置同步的情况下，每个面向用户的操作都可用。
- **同步非破坏性** — 同步失败或中断后，本地状态逐字节不变。
- **影响分析正确性** — 计算的传递性故障集合，与手工构造的图谱对照验证。

## 当前状态

规范与设计。Canonical 模型、一致性套件方案、仓储与密码学分层、以及每平台原生 UI 的决策已经定义。没有发布任何实现，也没有公开仓库，因此不显示代码链接。

## 我学到了什么

在任何实现之前先定义一致性套件，改变了规范必须包含什么。模糊的不变量无法被测试，因此写套件会倒逼规范变得精确——而一份精确到可测试的规范，也就精确到可以被实现三次。

第二个教训是，本地优先是一个会向外传播的设计约束。一旦同步不能是必需项，仓储层、身份模型与冲突语义都必须换一种设计方式——这正是该约束应当放在顶层、而不是某个设置开关里的原因。

## 下一步

- 把 canonical 规范作为独立文档发布。
- 在任何平台代码之前，先针对规范编写一致性套件。
- 先在一个平台上实现一次仓储层，验证离线完备性之后再加第二个平台。
