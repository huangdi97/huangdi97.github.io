## 概览

BioPulse 是面向生命科学商业化流程的 Agent-native 工作台。它在仓库里就把目标说得很直白：不是「加了 AI 的 CRM」，而是让智能体替人填表、替人盯异常、替人做推演。

公开目录树中包含一个 FastAPI 云服务、七个智能体包、一套分层安全护栏、带 RAG 接入的向量记忆，以及四个客户端——React 管理端、Web 端、Flutter 移动端与微信小程序。GitHub 检测到 MIT 许可证。

范围说明：本页不发布任何准确性数字、客户名或营收数据。这些都无法从外部核实。

## 问题

生命科学商业化团队跑在一套没人有时间维护的记录上。代表迟到且不完整地补录拜访，费用报销与它所属的拜访彼此脱钩，管理者拿着由这些残缺记录生成的看板去推断趋势。

由此产生两个后果，而且会互相放大：

- **稽核是回溯式的。** 拜访、费用与流向分散在不同系统里，彼此矛盾只能靠抽样发现，而不是靠结构发现。
- **提问要过人。** 「上周生物线商机转化怎么样」变成了向某个会写查询的人提需求。

这两者都是伪装成报表问题的协作问题。再加一块看板，哪个都解决不了。

## 为什么重要

一个能够行动的智能体——填表单、标异常、提方案——需要的约束要比「回答这个问题」更硬。在受监管的商业场景里，可接受的失败模式是沉默，而不是自信地编造。

因此本项目把分层安全护栏放在智能体运行时**旁边**而不是**之后**，也正因为如此，合规模块做的是拜访 × 费用 × 流向的交叉稽核，而不是对单一维度单独打分。公开测试中存在专门的 L1 / L3 护栏用例，这是本站唯一能真正指出的部分。

## 产品 / 研究主张

1. **智能体替代的是步骤，不是界面。** 价值单元是一个带着记录的完成步骤，不是一个回答框。
2. **稽核必须是结构性的。** 拜访、费用、流向三者交叉核对才是产品；月度抽样只是权宜之计。
3. **保守失败是默认行为。** 分层护栏处于写入路径之内，因此无依据的主张会被拒绝，而不是被软化。
4. **发布的能力必须等于发布的证据。** 没有基准测试的地方，就不写准确性数字。

## 系统设计

```text
智能体请求 → 安全档案 → 智能体运行时（循环 / 重试 / 熔断）
          → 工具桥接 → 领域服务 → 数据仓库
          → 稽核记录
```

运行时负责执行语义——循环、重试、错误分类、熔断、死信与指标；领域行为留在服务层。安全是分层的（测试中可见 L1 至 L3），而不是边缘的一道过滤器。

## 架构

**云服务。** `cloud/app` —— 智能体运行时、智能体定义、安全护栏、分析与推演评估、合规、数据仓库、路由与类型化 schema，以及数据库迁移。

**七个智能体。** 合规监控、异常分析、销售建议、销售教练、知识、商机扫描与竞品爬取，各自作为独立包位于 `agents/` 下。

**记忆与检索。** 向量记忆与 RAG 接入模块，`tests/agent_runtime` 中有对应测试。

**客户端。** `frontend/` React 管理端、`web/`、`mobile_app/` Flutter（SQLite 离线优先）、`weapp/` 微信小程序。

**交付。** `deploy/` 承载 Nginx + TLS、备份与 CI / CD 配置；据 README 技术表，监控基于 Prometheus。

## 核心能力

**七个可用智能体。** 各自独立成包，而不是一个大提示词加上若干开关。

**带不确定性表述的推演。** README 描述了带置信区间、回溯验证与平行对比的因果链。没有伴随发布基准测试，因此本页只陈述设计，不再多说。

**代表工作台。** 拜访排序、HCP 画像、竞品推送、语音填表、费用预审与拜访理由。

**跨域合规稽核。** 拜访 × 费用 × 流向交叉稽核，外加飞检与窜货检测。

**四端共用一个服务。** 管理端、Web、移动端与小程序接入同一云部署。

## 技术决策

**运行时优先，而非仅做编排。** 循环语义、重试与熔断都以代码形式存在并自带测试，因此失败行为属于契约的一部分，而不是框架默认值。

**安全分层。** L1 / L3 护栏与被它们约束的智能体分开定义、分开测试。

**移动端离线优先。** 设备端使用 SQLite，代表跑一天外勤不必依赖网络连接。

**既不伪造，也不省略。** 本页提到的每项能力都对应公开目录树中的一个目录；只有文字描述、没有实物可查的内容，会标注为「描述」而非「已验证」。
